01 · Architecture overview

Wrap the Code Puppy CLI in a service. Put it behind Azure AD.

Code Puppy is an open-source agentic coding assistant that normally runs in a developer’s terminal. We’re hosting the same engine inside our Azure ecosystem with a browser UI so any internal team can use it without provisioning API keys or installing the CLI.

Keys never leave Azure

The browser never sees an LLM API key. All provider calls go through the backend, which reads secrets from Key Vault at runtime.

🌐

Internal-only access

Reachable only from corp network / VPN. Entra ID groups gate who gets in; Application Gateway with WAF sits in front.

🤗

Same engine as the CLI

We import Code Puppy as a Python library and expose its agent loop over HTTP + WebSockets. No fork, no rewrite.

System diagram

02 · Setup steps

From CLI prototype to internal Azure app

Seven steps. Each one is a PR, a Bicep module, or a pipeline stage — nothing happens by clicking around in the portal.

  1. 1

    Containerize the Code Puppy backend

    Wrap the CLI/Python API in a small FastAPI service. Dockerfile pins Python, installs code-puppy, and exposes one HTTP and one WebSocket route.

  2. 2

    Build the web UI

    A small React SPA that mimics a terminal/chat: streaming tokens over WebSocket, file diffs as cards, approval buttons for tool calls.

  3. 3

    Provision Azure resources (Bicep)

    Container Apps environment, Container Registry, Key Vault, Log Analytics workspace, Static Web App for the UI bundle.

  4. 4

    Wire up Entra ID + networking

    App registration for the SPA and the API. VNet integration for Container Apps; private endpoint on the Static Web App; restrict to the cp-users group.

  5. 5

    Load secrets & provider config

    Key Vault references for LLM keys. Per-environment config map says which providers, tools, and shell commands are allowed.

  6. 6

    Stand up CI/CD

    GitHub Actions: build & test, security scans, build & push image to ACR, deploy to dev, smoke-test, approve, deploy to prod.

  7. 7

    Cut over & observe

    Onboard the first team. Watch Log Analytics for blocked policy events and token spend. Iterate prompts and policy via PRs.

Policy flow

⚙️

Implementation notes

  • Behavior is driven by a single policy.yaml per environment, mounted from Key Vault references.
  • Toggling a capability is a config PR, never a code change — same image runs in dev and prod.
  • Default is deny. New tools, providers, and shell commands must be explicitly added to prod.
📝

What we always log

  • Every tool call: name, args, allowed/blocked, duration.
  • Every model call: provider, model, token count, cost.
  • Every block event with the matching policy rule, so rules can be tuned with evidence.

What lives in git

  • Backend wrapper — the FastAPI service around Code Puppy.
  • Frontend SPA — chat / terminal UI, built to static assets.
  • Agent & prompt definitions — versioned, reviewed like code.
  • Policy & config — policy.yaml, feature flags, allow-lists.
  • Infra (Bicep) — Container Apps, Key Vault, networking.
🔬

How we tune safely

  • Prompt & policy changes ship as PRs, with diff review and CI checks.
  • Feature flags let us roll new tools out to a single team before everyone.
  • Dashboards on top of Log Analytics show allow/block ratios, token spend, and latency.
  • Auto-rollback on error-rate / latency SLO breach; manual rollback is one button.
The story in one line: the CLI you already trust, wrapped in a service you can audit, behind a UI any coworker can use — shipped the same way as the rest of our platform.
